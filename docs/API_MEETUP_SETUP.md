# Meetup travel and weather: setup and flow

The planner now helps a Kaki pair, one group, or two connected groups compare public meeting places. People still discuss, vote, propose and approve the final plan. An algorithm never confirms a meetup on their behalf.

## What users do

1. Open a meetup from their group or mutual Kaki conversation. Select the half-hour periods when they are available.
2. Optionally search OneMap for an **approximate public starting place**, such as an MRT station. Apply it to selected times and save. Different times can have different origins. The API exposes only the caller's own origin rows; route responses contain group totals, never other members' origin coordinates or labels.
3. Search for a public meeting place and add it to the board. The “Sheltered” checkbox is a participant's suggestion, not a verified property supplied by the mapping API.
4. Choose walking/public transport, a journey budget and optionally sheltered places. Press **Compare travel options**. The server compares a bounded shortlist of saved meeting places and time slots. Where every shortlisted option has fresh routes for all available participants, it ranks attendance first, then the number of journeys within the budget, combined journey minutes, and the longest journey. Votes break ties.
5. If the complete route matrix is unavailable, the whole shortlist keeps a clearly labelled straight-line-distance ranking. Supplementary route times can still appear. Missing locations, outside-Singapore origins, exhausted budgets or provider failures do not become zero-minute journeys. This compares the submitted alternatives; it is not an exhaustive global optimum across Singapore.
6. Vote or propose a time and place. Existing version checks and required approvals remain: a group host, both connected-group hosts, or both Kaki participants. Editing the plan requires fresh approvals.
7. On the selected proposal, check NEA weather and recent rainfall. “Getting there today” checks LTA train advisories, optional bus-stop arrivals and optional station crowds.

**Timing matters:** OneMap public-transport routes use schedules. The planning query uses a departure one chosen journey budget before the meeting; it is an estimate for comparison, not a guaranteed arrive-by itinerary. LTA arrivals/crowds describe travel now. A nearby rainfall station measurement describes recent rain, not future rain. NEA's 24-hour and four-day results are labelled national outlooks, rather than precise rain forecasts for that place and minute. No rain percentages are invented.

## Accounts and server configuration

You said you do not yet have OneMap or LTA accounts. Their credentials cannot be generated by Encore. Put the issued values in **`server/.env` locally**, using the fields below. They are intentionally absent from committed examples and frontend code. Restart the server after changes. Do not use a `VITE_` prefix for these fields or paste their values in chat.

```dotenv
# Preferred: automatic token renewal on the server
ONEMAP_EMAIL=
ONEMAP_PASSWORD=
# Alternative: manually issued token; normally expires after 3 days
ONEMAP_TOKEN=
LTA_ACCOUNT_KEY=
# Optional for local testing; recommended by data.gov.sg for production
DATA_GOV_SG_API_KEY=
# Local per-process request budgets, not paid upgrade subscriptions
ONEMAP_DAILY_LIMIT=1000
LTA_DAILY_LIMIT=1000
```

## Backend data flow and guardrails

`Authenticated planner → current meetup membership check → validate inputs → server provider adapter/cache → normalized aggregate results → recheck membership and board version → UI`.

- Credentials go only to the provider's fixed HTTPS host, in server headers or the OneMap authentication POST. Browser responses never contain provider tokens, account passwords, raw route geometry or individual origin rows.
- Provider requests time out after five seconds, reject redirects, coalesce identical reads and use bounded in-memory caches. OneMap search caches one day, routes fifteen minutes; LTA bus arrivals twenty seconds, train advisories one minute, crowds ten minutes. Weather caches match its slower updates.
- One refresh uses at most six places, twelve time/place alternatives and twenty-four route requests, with four simultaneous routes and a ten-second scheduling deadline. Larger boards or partial matrices fall back to distance. Daily budgets are local process guards; restarting a server resets them. They are not provider quotas, and multiple server processes need a shared limiter before scaling out.
- Local provider limits are conservative: OneMap sixty reads/minute; LTA thirty/minute; each defaults to one thousand fresh reads/day. NEA has a local one-thousand-read/day guard. A provider 429 pauses fresh reads for one minute. A cached fallback is explicitly marked `stale` with its fetch time; stale routes never determine the travel ranking.
- Missing credentials return `onemap_not_configured` / `lta_not_configured`; availability, votes and ordinary distance suggestions keep working. Provider failure messages do not expose upstream bodies or credentials.
- Meetup lists now query the caller's candidate groups/connections/Kaki threads in SQL, then recheck live membership and block rules. A former member cannot retain access through a historical match.
- API source attribution is displayed in the planner. Keep the source links when reusing these results elsewhere, and follow the providers' licences and attribution requirements.

## Added endpoints

All are authenticated and participant-scoped; responses use `Cache-Control: private, no-store`.

| Endpoint | Purpose |
| --- | --- |
| `GET /api/meetups/:id/locations?q=City%20Hall` | Search public addresses with OneMap. |
| `GET /api/meetups/:id/travel-suggestions?mode=transit&maxTravelMinutes=60&shelteredOnly=false` | Compare saved places and availability using routes where complete, or labelled distance fallback. |
| `GET /api/meetups/:id/transport?busStopCode=83139&trainLine=NSL` | Train advisories plus optional stop arrivals and line crowd levels. |
| `GET /api/meetups/:id/environment` | Forecast for the selected meetup and recent nearby rainfall. |

Existing meetup endpoints remain compatible. `GET /api/meetups/:id/weather` also supports the longer NEA horizons. `planningInput(user,id)` is an internal repository method and must never be returned directly from an HTTP handler.

Existing community/API tests cover the original planning and approval flows. Live OneMap/LTA requests require your account configuration; these have not been claimed as tested without those credentials.
